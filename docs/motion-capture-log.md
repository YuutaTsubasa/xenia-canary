# Motion capture: commit log

One line per commit on `claude/kinect-one`, in order, in plain words: what
it changes and why. The design is in [motion-capture.md](motion-capture.md).

| # | Commit | What and why |
| --- | --- | --- |
| 1 | docs: motion-capture design | Writes down how the Xbox 360 Kinect works (the title tracks skeletons itself from raw camera frames), what Xenia and others already have, and the plan: one motion-capture API with Kinect v1, Kinect v2 and webcam backends under it, feeding an emulated Kinect v1 camera. No code yet; waiting for review. |
| 2 | docs: record the rewrite decision | The Kinect v1/v2 Windows code and the v2 depth reprojection in Free Riders were written by knuckleslee, so they can't simply move into a BSD project. The user chose to write them anew here from public sources (Kinect SDK reference, libfreenect) without opening those files. The design now marks which parts are rewritten and which are ported. |
| 3 | hid/motion: frame types and the device interface | Adds a new small library, `src/xenia/hid/motion`. `motion_types.h` describes what any camera device hands over (a depth picture in millimetres, a colour picture, the lens of each, optional tracked bodies with the console's 20 joints, the floor). `motion_device.h` is the shape every backend will have: open, close, "what can you do", "are you working and if not why", "give me your newest frame", and optionally the tilt motor. `NullMotionDevice` is the "no device" case. Nothing calls it yet, so Xenia behaves exactly as before. |
| 4 | hid/motion: MotionCaptureSystem under the input system | Adds the one place the emulator will ask for camera frames, owned by `InputSystem` like the existing Skylanders portal. A new option `motion_device` (in the HID section of the config: `none`, `auto`, `kinect_v1`, `kinect_v2`, `webcam`; default `none`) says which device to use. The device is only opened the first time a game asks for it, because most games never do and a camera takes a while to start. There are no backends yet, so any choice other than `none` just logs "not available in this build". With the default, nothing changes. |
| 5 | docs: rewrite the camera driver too | The user chose to write the game-facing camera driver (`PsCamDeviceRequest`) from our own tracing instead of building on knuckleslee's Xenia branch. The design now says how: we read how a game's Kinect library calls the driver and write each finding, with where we saw it, into `docs/kinect-pscam.md` before writing code. |
| 6 | docs: PsCam protocol notes | Before writing the game-facing camera driver, we traced how Sonic Free Riders' Kinect library calls it and wrote the findings down: the request codes (state, start, stop, read frame, calibration, timing, colour settings), the request block layout, the start-up and shutdown order, and how frames come back through a callback. Each fact says where it was seen and how sure we are. Important for later: the driver must finish every pending frame request after "stop", or the game hangs when it quits. Only one game has been traced so far. |
| 7 | docs: what the depth pixels mean | Traced where the game's skeleton tracker reads the depth picture. It shrinks the picture to 80x60 blocks, looks each value up in the table the driver gave it (request 24), and treats the answer as millimetres; 0 means "no reading". So our emulated camera can simply hand over millimetres with a one-to-one table, and does not need to imitate the Kinect's raw disparity values. The design is updated to match. Still unknown: the colour format (Bayer or YUV). |
| 8 | hid/motion: virtual Kinect v1, depth side | The first piece of the "virtual Kinect v1": it turns a depth picture (already in the v1's 640x480 view) into the exact bytes the game's Kinect library reads, high byte first, left to right as the sensor sees it, in millimetres; readings too far away are capped so the game sees "far" instead of "broken". It also builds the table the game asks for with request 24, mapping each value to itself, so the game's conversion leaves our millimetres alone. Comes with the first unit tests for this work (`xenia-hid-motion-tests`, all passing). Colour and lens reprojection come later. |
| 9 | hid/motion: depth reprojection into the virtual v1 | A Kinect v2 (or any other depth camera) sees the room through a different lens, at a different size, from a slightly different place than a Kinect v1. Stretching its picture would distort the player, so instead each depth pixel is turned into a point in space, moved to where the virtual v1 stands, and photographed again through the v1's lens (its focal length is published in Microsoft's Kinect SDK); where two points land on the same pixel the nearer one wins, like a real camera. Lens distortion is removed first, or a device can hand over its exact pixel rays (the v2 SDK can). Each point covers as many pixels as it needs so there are no holes. Six new tests draw scenes (a wall, a box in front of it, the camera moved, a point behind the camera) and check the result; all pass. |
| 10 | kernel: PsCamDeviceRequest answers "is a camera there?" | The first piece of the game-facing camera driver. Until now the kernel function games use to talk to the Kinect camera didn't exist in Xenia. Now it answers request 0 ("what state is the camera in?"): "no camera" when `motion_device` is `none` or the device can't open, "ready to start" when it opened. Every other request either says "no camera" or logs "not handled yet". With the default setting games see exactly what they saw before: no Kinect. |
| 11 | kernel: PsCam start, stop and simple set-up requests | The driver now answers the quick set-up requests a game sends before streaming: start (27) and stop (2) — and request 0 now says "streaming" between them —, request 33 (meaning unknown, the game ignores the answer), the depth table (24: each value maps to itself, because our frames are already in millimetres) and the timing info (25: 30 frames a second; one field left at zero tells the game not to try to lock its clock to the camera's, which a virtual camera doesn't have). Still missing: calibration (11/13/14), colour settings (35/36) and reading frames (5). |
| 12 | kernel: move the camera driver into KinectCamera | No behaviour change: the driver's code moves out of the kernel export file into its own small class, `KinectCamera`, which the kernel owns (next to the existing NUI state). Why: reading frames needs a background worker, and Xenia doesn't stop background helpers when a game ends; giving the driver an owner that is shut down before the kernel's memory goes away avoids crashes on exit. The export itself is now one line. |
| 13 | kernel: PsCam frame reads | The heart of the camera: the game asks for frames with request 5 and gets told "pending"; a small background helper ("Kinect Camera") waits for a new depth picture from the motion-capture system, redraws it through the v1's lens if it came from another camera, writes it into the game's buffer with a frame number, and then calls the game back to say "your frame is ready" — the same way the real driver does. When the game says "stop", every waiting request is answered "cancelled", because the game refuses to quit until all of them are answered. Colour requests are accepted but only answered at stop, since we don't know the colour format yet; the game's tracking uses depth only. Not yet tried in a game: there is still no real device backend. |
| 14 | kernel: PsCam calibration and colour-settings answers | Another tracing pass showed what the game does with calibration: it is only used to line the colour video up with the depth picture, never for tracking, and if the camera refuses it the game gets stuck retrying its start-up forever. So the driver now answers: version 4.0 (13), which makes the game ask for the older, simpler calibration (11); and that calibration as all zeros, which the traced code handles without any division or invalid number. Every byte of the answer is written, because the game does not clear it first. Colour-camera settings (35) are declined with the one answer that makes the game stop asking. The trace notes are section 12 of `docs/kinect-pscam.md`. |
| 15 | motion: skip pixels with no ray | A Kinect v2 says which direction each of its depth pixels looks in, with a table. If an entry in that table is not a real number, the reprojection used to compute nonsense from it; now that pixel is just left out, as if the camera had seen nothing there. A new test covers it. |
| 16 | motion: Kinect v2 direction table to rays | The Kinect v2 software can hand over a table saying, for each depth pixel, which direction it looks in. Its axes point the other way from ours (its "left" is the sensor's own left and its "up" is up, while our pictures count right and down), so this turns the table round. Tests check that something on the sensor's left ends up on the left of the picture the game gets, something above ends up near the top, and that an empty table (what the software gives before the sensor is ready) is not mistaken for a real one. No Kinect is needed for this part. |
| 17 | motion: our own declarations of the Kinect v2 SDK interfaces | Microsoft's Kinect v2 software is talked to through "COM interfaces": lists of functions in a fixed order. Instead of needing Microsoft's SDK to build Xenia, this file writes down just the functions we use, in the SDK's order, so the game-player's installed Kinect runtime can be used directly. The order was checked by a script against the public SDK header, interface by interface. |
| 18 | motion: the Kinect v2 device | With `motion_device = kinect_v2` (or `auto`), Xenia now loads the Kinect v2 runtime when a game first asks for a camera, waits up to 5 seconds for the sensor, and then keeps the newest depth picture plus each pixel's direction on its own thread. The game-facing driver redraws that picture as a Kinect v1 would see it. If the runtime isn't installed or no sensor shows up, the log says so in plain words and the game sees no Kinect. Not yet tried with a real Kinect v2: this PC has none. |
| 20 | docs: how the game uses the tilt motor | A fourth reading of the game's code, this time of how it moves the Kinect's motor and checks whether a Kinect is plugged in. The most important findings: as long as the motor reports "moving", the game keeps restarting its body tracking, so a fake motor must never stay "moving"; the game itself never tilts the camera, only its Kinect library does once at start; and one bit of the device status decides whether the Kinect parts of the game run at all. Notes are section 13 of `docs/kinect-pscam.md`. |
| 21 | motion: a pretend tilt motor | A Kinect v2 or a webcam has no motor, but games ask the Kinect to tilt. This is a pretend motor: it goes straight to the angle asked (never "still moving", because the game restarts its body tracking while the motor moves), stays within the real one's range of -27 to +27 degrees, and reports a matching pretend gravity reading so the game believes it arrived. It also remembers the floor the game tells it about. The real camera does not move, so its picture stays as it is. Tests check the angle the game would read back for every position. |
| 22 | kernel: the game sees the pretend motor and a ready Kinect | When a motion-capture device is chosen, the Xbox system functions games use for the Kinect now answer from it: "is a Kinect connected and ready" says yes while the device runs (before, it only followed a setting in the console options); the motor status reports the pretend motor (not moving, matching gravity, the remembered floor); and the four motor functions Xenia was missing (set angle, stop, remember the floor, report status) now exist. With motion_device = none everything behaves as before, apart from those four new functions answering "no Kinect". |
| 23 | motion: a pose model's points become a skeleton | First piece of the webcam path, brought over from Free Riders Recompiled (Yuuta's own code there, so it can come under Xenia's license). A pose model finds 17 points on a person in a webcam picture (nose, shoulders, elbows, wrists, hips, knees, ankles...). This turns them into the 20 joints a Kinect skeleton has, making up the ones the model lacks (wrists, feet, spine, centre of the hips and shoulders) from their neighbours. A webcam cannot tell how big or how far away someone is, so every player comes out the same size, 2.5 m from the sensor. Pictures from cameras that mirror (like a phone's selfie view) can be turned back. The Free Riders tests came along too. |
| 24 | motion: steady the pose points | Also from Free Riders (Yuuta's code). A pose model looks at every webcam picture afresh, so even a hand held still jumps by a pixel or two between pictures; drawn into the Kinect's depth picture, the game would see a trembling body. This filter (the "1 Euro filter", a well-known one from a 2012 paper) smooths a still point hard but lets a real movement through at once, so the body doesn't lag. Changes from Free Riders: its two settings no longer come from environment variables; the defaults are the ones Free Riders uses. |
| 25 | motion: read MediaPipe's answers | Also from Free Riders (Yuuta's code). The webcam uses two small neural networks from Google's MediaPipe (as converted by OpenCV Zoo, Apache-2.0 licence): one finds where a person is in the picture, the other then finds their 33 body points in 3D. This part does everything around the networks except running them: shrinks and turns the picture into what each network expects, turns the detector's thousands of guesses into one crop around the best person, and turns the pose network's numbers back into points in the picture with a depth in metres. It also keeps the crop the network suggests for the next picture, so the detector only has to run when the person is lost. Change from Free Riders: pictures are now RGBA (what Xenia's motion types use) instead of BGRA. |
| 26 | motion: draw a depth picture from a skeleton | New code (Free Riders never needed this: there the game was handed the skeleton directly). A webcam sees no depth, but the game's own body tracker only reads depth pictures. So the skeleton from the webcam is drawn as a simple body (rounded tubes for the limbs, a ball for the head, a wider torso) standing in a bare room with a floor 0.9 m below the sensor and a wall 3.8 m away, exactly as the pretend Kinect v1 camera would see it. It can also draw the view with the pretend motor tilted. Tests check distances in the drawn picture (wall, floor, chest, an outstretched hand on the correct side, the gap between the legs, the tilted view). Still experimental: whether a game's tracker accepts a drawn body is only known once tried. |
| 27 | third_party: ONNX Runtime headers | The pose networks are run with Microsoft's ONNX Runtime (MIT licence), the same engine Free Riders uses. This adds only its six header files (version 1.30.0, unchanged), which describe how to call it. The engine itself (a DLL of tens of megabytes) is not added to the repository or built: Xenia will look for it only when someone picks the webcam, and say in the log if it isn't there. |
| 28 | motion: run the pose networks | Also from Free Riders (Yuuta's code). This is the part that actually runs the two MediaPipe networks on a webcam picture: the person detector only when it doesn't already know where the person is, then the pose network on a crop around them, whose answer also says where to look in the next picture. ONNX Runtime is looked for in a "pose" folder next to Xenia (or the folder the new `motion_pose_folder` setting names), together with the two model files. Anything missing gives a plain message in the log, e.g. "The pose model … is missing" or "The ONNX Runtime found is version 1.17.1, too old" (Windows 11 carries its own old copy). Tried here with the real models and ONNX Runtime 1.30 from the Free Riders folder: they load and correctly find no one in a grey picture. Not ported: Free Riders' older single-network model (RTMPose), which Free Riders itself no longer uses by default. |
